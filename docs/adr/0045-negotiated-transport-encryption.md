# 0045 — 服务端决定握手后的传输加密模式

状态：已采纳

Supersedes: [0043](0043-client-aead-transport.md) 中客户端握手后始终使用 AEAD，以及 Auth 发送原始 PSK 的决策。密钥生成、索引、范围授权及加密记录格式保持不变。

## 背景

管理台需要在服务配置中控制客户端与服务端握手后的通信是否加密，客户端无需另配开关。

## 决策

- 新增运行时配置 `transport_encryption`，默认 true，按独立段持久化。旧库缺少该段时保持开启；API 保存省略该字段时保留当前值。
- 每条新连接从服务端原子快照读取开关。保存即时影响后续握手，既有连接保持原模式，重连后采用新模式。
- 两种模式均完成 auth_key 双向证明。握手版本升至 2，ServerHello 在随机数后增加 mode 字节（0 明文、1 AEAD）。mode 纳入 HKDF transcript，双方 HMAC 证明同时认证所选模式，客户端不接受未知模式，也不在握手失败后回退到明文。
- AEAD 模式继续使用 ChaCha20-Poly1305 记录；明文模式在证明完成后直接传输 yamux 字节。明文模式的业务数据没有保密或完整性保护。
- Auth 的 `key` 字段改为握手中已证明的 key_id 的小写十六进制编码，两种模式都不传输原始 PSK。服务端比较传输身份，再从现有 O(1) 索引取密钥执行范围授权及撤销校验。公开标识无法单独建立认证连接。
- 原有 vn-v1 用户路径仍仅接受 UserAuth；关闭加密也不允许跳过传输证明的旧客户端 Auth。

## 兼容性

BREAKING：v1 和 v2 传输握手不兼容，服务端和内网客户端需同步升级。DMP 帧头、消息编号、数据库密钥和客户端 auth_key 配置不变。配置库无需迁移。

## 验证

覆盖后台开关读写与省略字段、配置重载、两种传输模式、模式篡改、错误密钥、范围授权、切换后既有连接通信及明文 Auth 不泄露 PSK。保留既有重放、记录篡改、取消与并发测试。
